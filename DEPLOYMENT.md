# Physics literature digest deployment

The fork runs on GitHub-hosted Ubuntu with Python 3.13 and CPU PyTorch. The repository's weekly configuration uses theme-balanced embedding recall followed by the `reading_value` recommendation policy; the original embedding algorithm and score policy remain available. Scheduled trigger: `37 1 * * 1` (09:37 Asia/Shanghai). The minute avoids the top-of-hour and 00:00 UTC peaks, when GitHub delays scheduled jobs most (the earlier `15 0 * * 1` slot started 4–6 hours late); this is a trigger time, not a guaranteed mail arrival time. GitHub can also pause all workflows on a fork; the Actions page then shows a banner and a maintainer must re-enable them.

## Repository settings

Actions Secrets: `ZOTERO_ID`, `ZOTERO_KEY`, `OPENAI_API_KEY`, `OPENAI_API_BASE`, `SENDER`, `RECEIVER`, `SENDER_PASSWORD`.
Actions Variables: `CUSTOM_CONFIG` (optional non-sensitive YAML merged over repository defaults), `SMTP_SERVER`, `SMTP_PORT` (465 default), `DELIVERY_ENABLED`.

`CUSTOM_CONFIG` must contain environment references for credentials, never credential values. The workflow does not print it. All credential values belong in Secrets.

The deployed language is Chinese. Abstract-confirmed facts and facts confirmed by the supplied full-text excerpt must be distinguished; the input is capped to 4,000 tokens and is not a complete-paper review. English titles, authors, arXiv publication date/journal metadata and original/PDF links are rendered separately. Summary length and required Chinese fields are validated; at most one repair request is made using the original evidence. Its feedback specifies the actual Chinese-character count, missing/duplicated fields and invalid evidence markers, including the exact permitted excerpt IDs. An empty initial response can use this same single repair; diagnostics never log model drafts. Failed, empty or still noncompliant summaries stop delivery; every named Chinese field must have a valid evidence label, an explicit speculation label or an unavailable-evidence statement. Full-text labels identify an existing supplied excerpt. These checks validate provenance and format rather than factual entailment; noncompliant summaries are never quietly replaced by English abstracts. Author affiliations are disabled to avoid a second LLM request per paper.

## Complete SMTP setup

Use the repository Settings / Secrets and variables / Actions pages, or `gh secret set NAME -R nwh-phy/zotero-arxiv-daily` with secure interactive input, for sender address, receiver address and SMTP app password. Set `SMTP_SERVER` and `SMTP_PORT` as variables. Never provide a mailbox login password or put credentials in YAML.

Run the `Test` workflow. Its native tests are offline; its live checks cover Zotero, CPU embedding, arXiv, ranking, LLM, Chinese summary, HTML rendering and SMTP authentication. Missing SMTP is explicitly BLOCKED. By default Test does not send email. The optional `send_test` input sends one explicitly labelled deployment test only after all requested checks and SMTP authentication pass; historical samples are labelled as such. SMTP acceptance does not prove inbox arrival. The optional `summary_only` dispatch input retests the summary stage after a summary-only fix; skipped stages must be assessed against the earlier full-run evidence. The full verification shares the 180-minute CPU budget used by weekly delivery; hundreds of abstracts can exceed 40 minutes on a GitHub runner. Verification artifacts are retained for 14 days. The abstract-only sample uses a real paper from the configured current arXiv window; a separate full-text sample checks section extraction and valid excerpt citations when available. Unavailable full text is explicitly SKIP; on empty RSS days, a separate arXiv API query supplies real historical records solely for verification. These are labelled as historical samples and never sent by the production workflow; an explicitly requested deployment test may send one labelled historical sample.

Only after SMTP authentication succeeds, set `DELIVERY_ENABLED=true` and manually run `Send weekly literature brief` to verify actual email delivery. If credentials are missing, preflight lists only their names. Until then, the weekly job is deliberately skipped.

## Operations and limits

Keep Alive commits a timestamp monthly to retain repository activity. Native CI tests exclude the model-download test; the Test workflow explicitly exercises the configured embedding model on Ubuntu. Both uv dependencies and Hugging Face downloads are cached. Jobs have bounded timeouts, and LLM retries are limited. arXiv API throttling (HTTP 429/503, common on shared runner addresses and observed for over 14 minutes on 2026-10-20) waits for `Retry-After` or backs off 30–600 seconds, for at most ten attempts per page (about 65 minutes) before the run fails. Requests identify the project in their User-Agent. Per-paper checkpoints are restored before processing and saved even after ordinary job failures; cache service errors do not block processing or successful-delivery markers.

No new candidates means no email. With delivery history enabled, an empty successful retrieval still advances its UTC coverage cursor. A China-date cache marker is saved after SMTP accepts the message, and delivery runs are serialized. This is best-effort duplicate suppression, not transactional exactly-once delivery: cache eviction, cache-save failure or interrupted SMTP acceptance can allow duplicates. Do not blindly rerun a delivery job when SMTP acceptance is uncertain. SMTP acceptance does not establish recipient inbox arrival.

Zotero access is read-only. Corpus filtering uses existing physics-oriented collection paths. No server, Docker or paid embedding resource is provisioned. The LLM reuses an existing OpenAI-compatible service; its availability and quota remain external dependencies.

Weekly delivery: Monday 09:37 Asia/Shanghai (UTC cron `37 1 * * 1`). The first production attempt retrieves all pages for new submissions in the preceding seven complete UTC days and records that attempted start before fetching. If this very first attempt fails, a later retry starts at that original boundary instead of forgetting the failed week. Attempted start and successfully completed coverage are separate; previews never create or advance either record. Later runs start at the last successfully completed coverage boundary minus a two-day overlap, including matching cross-listed categories. Failed weeks are backfilled rather than silently skipped; a gap over the configured 90-day limit stops explicitly until the limit is raised. Boundaries are UTC midnight (Beijing 08:00). Old-paper revisions are excluded. Abstracts enter a bounded reading-value shortlist after theme-balanced ranking and additional core-topic recall. Full-text extraction and review are attempted for focus candidates; only confirmed focus papers receive the strict Chinese summary. A delayed API index may omit papers; this does not guarantee exhaustive coverage. Timeout is 180 minutes for the larger weekly CPU workload.

Summary generation uses `kimi-k3-1` through the existing Responses service, with low reasoning effort and a 4096-token output budget. The summary itself remains 150–250 Chinese characters. The embedding model and seven-day retrieval window are unchanged; ranking uses the configurable theme-balanced policy described below.

The weekly brief now uses the China-edition Kimi K3 model `kimi-k3-1`. Its dedicated WorkBuddy key `zotero-weekly` is pinned to China edition and only allows that model. The key is stored solely in this fork's Actions OPENAI_API_KEY secret; the CC Switch provider remains unchanged.

## Recommendation, evidence and resume behavior

The fork enables `reranker.ranking.mode: theme_balanced`. Zotero paths are grouped at depth two (for example `20_主题/EELS` or `30_方法/电镜理论`). Each candidate is scored against up to three nearest references within each theme, weighted by actual elapsed days between Zotero additions with a 180-day half-life. Multi-collection papers are counted once within each theme. When `include_path` is set, only the collections it matches form themes; a reference's other collections are kept for traceability but neither create themes nor win recommendations. Soft penalties reduce repeated winning themes and near-identical candidate abstracts; no theme receives a compulsory quota. The order can therefore differ from descending raw similarity. The reading-value email labels the source as “匹配收藏夹”, shows related reference titles, and puts “收藏相似度” in a secondary traceability line. A collection name does not establish the paper's method, and an embedding score is not a calibrated scientific relevance measure. Set the ranking mode to `legacy` to restore the original embedding score/order.

### Reading-value policy

The weekly repository configuration enables `reranker.relevance.policy: reading_value`. The shortlist takes the first 40 unique papers in embedding order and adds up to 20 further papers matching the configured `shortlist.core_patterns`; unused slots are filled in embedding order. The unique shortlist never exceeds `top_k: 60`. Patterns widen recall for methods and current physical questions; a match alone never earns a recommendation. The model must state the actual contribution, the specific target or physical question, how the researcher can use the work, and a verbatim quotation from the supplied title or abstract. The source-substring check tolerates whitespace differences but rejects fabricated, translated or stitched quotations. Routes are `current`, `method`, `exploration` and `exclude`. The public profile describes research questions and transferable methods without personal identity or raw experimental data.

The default recommendation caps are `focus_limit: 6` and `explore_limit: 2`, further bounded by `executor.max_paper_num`. Current-question or method candidates scoring 4–5 can enter the focus group; 3-point candidates and explicitly exploratory work can enter the explore group. Empty slots remain empty. Each focus candidate must pass a separate review of the supplied numbered body excerpts before appearing as “重点推荐”. A confirmed review cites available excerpt IDs and preserves the explicit reading use. Review may reject the candidate or downgrade it to “拓展阅读”; unavailable body text also downgrades it rather than claiming full-text confirmation. This is an excerpt review, not a complete-paper review. Focus cards lead with the intended use, target question and actual contribution, followed by the strict 150–250-character summary and its source labels. Explore cards contain only the contribution, intended use and title/abstract quotation; they do not request or display the full Chinese summary.

Every shortlisted paper must finish abstract screening, and every requested body review must finish without request or validation failure. Failed/skipped screening or review blocks SMTP and coverage/history advancement; no unjudged paper fills a slot on similarity alone. A partial diagnostic preview is labelled “筛选未完成，暂不投递”. Before preparing SMTP or delivery history, the delivery assertion requires both completion flags, unique paper identities, and that every selected paper passes the same eligibility checks and configured group limits used by the renderer. A paper silently omitted from a diagnostic preview cannot remain in a delivery's history list. A complete screening/review with no recommended paper may advance coverage without sending an email. Successful abstract judgements and body reviews have separate resumable caches with input/policy/prompt/settings digests; failed responses are retried rather than cached as usable recommendations. A downgrade for unavailable body text is reported explicitly.

The abstract-screening path was verified with the real configured provider on 2026-11-05 at commit `e649ff2`: [10-27 replay](https://github.com/nwh-phy/zotero-arxiv-daily/actions/runs/41969826513) and [11-02 replay](https://github.com/nwh-phy/zotero-arxiv-daily/actions/runs/41969853958). Both scored 60/60 papers with zero failures or skips. The first produced four focus candidates and two exploration candidates in 537.57 seconds; the second produced one focus candidate and two exploration candidates in 423.58 seconds. Across the two historical selections, seven papers were retained, two added and twelve removed. These are provisional abstract selections: the replay does not retrieve body excerpts, execute focus review or send email. Source-quotation validation checks that cited text exists, not that every generated statement is correct. An independent abstract check found a mistranslation of “gapless” and an overly strong claim that an optical denoising method transfers directly to EELS. Full body-review/summary behavior with the real provider, SMTP, production operation and user-rated recommendation quality remain unverified for this change. The local and Ubuntu PR regression suites passed 373 tests, with one model-download slow test deselected.

### Original score policy

Set `reranker.relevance.policy: score` to retain the original second stage. With `top_k: 30`, the top 30 papers of the embedding order are each sent, as title and abstract only, to the configured summary model with the plain-text `profile`; the model returns a 1–5 score and a short Chinese reason, shown in the email as "LLM 判断". Papers scoring at least `min_score` (3) are recommended in descending score, embedding order breaking ties, up to `executor.max_paper_num`; a brief can therefore contain fewer papers. A paper whose judgement fails stays eligible after all passing ones, in embedding order, and is shown as "LLM 评分不可用，按相似度补选"; it is never counted as passing. The report and email separate attempted, scored, failed and threshold-passing judgements and the number of unscored papers selected. If fewer than half are scored, the embedding order is used, the email says so, and successful judgements stay in the report for diagnosis. If no candidate passes and no failed judgement is eligible, no email is sent and coverage advances (`no_relevant_candidates`). Successful judgements are cached per paper (`relevance-*.json`), keyed by paper identity, title and abstract, profile, model/generation settings, endpoint and prompt; changing any of these invalidates the entry. Failures are never cached. The relevance stage has bounds: `request_timeout` (90 s), `max_retries` (1), `max_tokens` (4096), `max_consecutive_failures` (5), and `time_budget_seconds` (900); no request starts whose worst case would pass the budget. Skipped judgements are treated like failed ones under this original policy. To restore its former full configuration, also set `top_k: 30` and `executor.max_paper_num: 10`; switching only the policy retains the currently effective limits. These judgements are model opinions. Delivery history keeps the IDs/titles of the last accepted brief; the next run reports how many are now in Zotero by arXiv ID or normalized title, in any collection.

Summary input remains capped at 4,000 tokens. TeX preambles/comments are removed, nested input/include files are resolved relative to the source bundle with cycle/depth/size bounds, and conclusion, results/discussion and methods sections are preferred over introductory text. TeX headings may contain nested braces such as `\label{}` or `$_{2}$`; labels are removed from section names. Markdown headings and common plain-text headings are supported. When headings cannot be recognized, both ends of the body are sampled and labelled as unrecognized sections; this does not establish that a conclusion section was found. Bibliography, acknowledgements and other back-matter sections (data availability, author declarations or contributions, competing interests, funding) are excluded. The reader-facing email removes repeated abstract-confirmation tags, compacts full-text citations to `[E1]` and lists the cited excerpt IDs/section names in one source line per paper. Speculation and unavailable-evidence wording remain visible. The original summary and its complete labels are retained unchanged for validation and checkpoint reuse. Full-text claims must use an existing label such as `[全文片段确认:E1]`; unavailable IDs and bare full-text confirmation labels fail validation. Every field is checked independently for its label or explicit unavailability; these checks establish source availability and format, not semantic correctness of every claim.

`executor.progress_dir: .paper-progress` enables local checkpoints. Set it to `null` to disable. Checkpoints are partitioned by library ID and paper metadata/version, and store extracted body text, validated summaries and safe processing/error status. Credentials, resolved configuration and Zotero reference titles are not stored. Model/endpoint, prompt/quality rules, evidence-selection version or input changes invalidate summary reuse. Extractor changes require an `EXTRACTOR_VERSION` bump; changes to summary input or evidence selection require an `EVIDENCE_VERSION` bump. Repair-feedback changes that retain the same original input, policy and acceptance rules preserve already validated summaries; they do not require repeating successful work. A corrupt checkpoint is ignored. Files are written atomically; extraction can be reused when summary generation fails. Completed summaries are checked again before reuse and strict validation runs before delivery. Failed selected papers do not prevent the remaining selected papers from saving progress, but they prevent email delivery. Cache restoration never marks an email as delivered.

GitHub Actions restores `.paper-progress` from the most recent available repository cache and writes a new cache key per run/attempt, including failed runs. Cache eviction, cancellation or hard runner termination can lose progress; this is best-effort resumability. Keep `.paper-progress` when retrying: it also contains coverage and pending-SMTP history, so clearing it can discard duplicate-suppression and reconciliation evidence. Use a separate progress directory for an isolated fresh preview. Overrides changing the production progress directory must also update the workflow cache path. Coverage history and the SMTP date marker remain separate mechanisms; coverage/history correctness across hosted runners still depends on successful cache persistence/restoration.

## Coverage, duplicate suppression and SMTP uncertainty

The fork enables `executor.history_enabled: true` for weekly arXiv-only retrieval. History lives beside per-paper checkpoints, partitioned by library, receiver, arXiv categories and cross-list setting. After SMTP acceptance, all retrieved/evaluated paper IDs are remembered, including papers below the recommendation cutoff. This prevents the overlap window from recycling last week's unselected papers. Late-indexed records that have not been seen remain eligible. arXiv versions and HTTP/HTTPS URLs share an article identity. IDs are retained for 120 days; no overlap setting should exceed that retention window. A changed receiver, category list or cross-list setting starts an independent coverage history. Zotero `include_path`/`ignore_path` changes only affect ranking and keep the same history: earlier versions keyed history by collections too, which made the 2026-10-19 rerun after a scope change re-send 6 of 10 papers. When no current history exists, the earlier `history-*.json` files of this subscription are merged once. Their names hashed the include/ignore lists too, so they are found only by recomputing names from `executor.legacy_history_scopes` (the collection lists of the 2026-10-19 deliveries) together with the current receiver, categories and cross-list setting; histories of any other subscription in the same directory are never read. The merge takes the union of evaluated IDs, the latest coverage boundary and the newest last delivery, and records `migrated_from`; the earlier files are left unchanged. A single uncertain batch is carried over. Several uncertain batches block sending but can each be inspected and reconciled by exact batch ID, inside their own earlier file. Confirming an older batch as accepted adds its papers without moving a later coverage boundary back. An unreadable earlier file stops delivery. Saved histories include a non-sensitive scope summary (categories, cross-list); the receiver remains only hashed in the file name. Coverage only advances after successful delivery or a genuinely complete no-new-candidates run. Corrupt history fails closed, and a local POSIX lock prevents concurrent sends using the same history.

Before submitting a message, the intended batch is written to history with a deterministic Message-ID. A connection, TLS, authentication or explicit SMTP rejection clears that pending batch and allows a retry. A disconnect/timeout during submission leaves its outcome uncertain and prevents automatic resending. A failure during QUIT does not undo prior DATA acceptance. If SMTP accepted but history cannot be saved, the workflow date marker is still written when possible, and the pending batch must be reconciled. Neither a Message-ID nor a cache marker guarantees exactly-once SMTP delivery or recipient inbox arrival.

The `Reconcile uncertain literature delivery` workflow defaults to inspection and never sends mail. First inspect its pending batch ID, then check independent SMTP or recipient evidence. Only with that evidence, run it with the exact batch ID and `accepted` or `not-accepted`. A mismatch changes nothing. Locally, with the normal environment/configuration loaded, use:

```bash
uv run --frozen scripts/reconcile_delivery.py --outcome inspect
uv run --frozen scripts/reconcile_delivery.py --outcome accepted --batch-id EXACT_BATCH_ID
# Or --outcome not-accepted only after confirming rejection/non-acceptance.
```

Cache eviction, restoration failure, hard cancellation and the unavoidable SMTP/persistence gap can lose history. The protections are best effort on GitHub Actions, not a transactional delivery system. Keep independent evidence when investigating uncertain sends; do not clear history merely to make a rerun proceed.

## Preview and operational evidence

Run locally with `executor.dry_run=true`, or select `dry_run` when dispatching the weekly workflow, to render a preview without SMTP, delivery markers or coverage advancement. Required provider/library configuration still needs to be available. A preview may populate the reusable extraction/summary cache; it does not mark candidates as evaluated for delivery. A dry-run dispatch works while `DELIVERY_ENABLED=false` and ignores a prior successful same-day marker. Scheduled jobs continue to respect that gate. `executor.output_dir` defaults to `verification/brief`; `brief.html`, `brief.txt` and an aggregate `report.json` distinguish preview, no-candidate, failed, uncertain and SMTP-accepted outcomes. The weekly workflow retains report artifacts for 14 days and posts aggregate counts/duration to its job summary. HTML/plain-text artifacts contain recommendation/reference content and should be handled as personal literature data; resolved secrets/configuration are never included.

For a complete preview of the selected branch's recommendation settings before updating the production override:

```bash
gh workflow run main.yml --ref BRANCH -f dry_run=true -f repository_recommendations=true
```

With both inputs enabled, the configuration step exactly replaces `reranker.relevance`, `executor.max_paper_num` and `llm.summary_instructions` with their checked-out repository values. Other explicit `CUSTOM_CONFIG` settings, including models, API environment references, Zotero collections and delivery/history configuration, remain in effect. Missing repository values stop the run before configuration is written. The default input is false; scheduled runs and sending runs always retain the ordinary override behavior.

`report.json` records per-stage seconds in `timings` (retrieval, zotero, ranking, relevance, reading_review, extraction, summaries, delivery), local-embedding `ranking` stats (model load, encode, encoded texts), relevance counts including cache reuse and final `focus_count`/`explore_count`, and `history.migrated_from`. Its `reading_review` section records `complete`, `attempted`, `confirmed`, `downgraded`, `rejected`, `unavailable`, `failed`, `skipped` and `reused`; the Actions summary reports these aggregates without paper bodies. A failure before the brief is rendered, such as arXiv throttling, still writes `report.json` with a failure status, stage and safe error type, never upstream error text.

Each run that ranks candidates also writes `evaluation.json` beside the report: every candidate's title, abstract, stage-1 rank, embedding score and theme, relevance judgement and selection; the reference library as ranked (title, date, theme paths); the exact embedding similarity matrix (base64 float32, about 1 MB for a 450-paper week; rounding to 4 decimals had flipped near-tied picks below rank 240 in a real week); and the effective ranking/relevance settings, prompt digest, model names and commit. It contains no credentials or endpoint. To build a fixed evaluation sample, download a run's artifact into the Git-ignored `verification/` tree (artifacts expire after 14 days), then:

```bash
uv run --frozen scripts/evaluate_ranking.py verification/eval/RUN/evaluation.json --template labels.csv
# label rows 精读 / 浏览 / 不相关 (including some of ranks 31–80), then
uv run --frozen scripts/evaluate_ranking.py verification/eval/RUN/evaluation.json --labels labels.csv \
  --set theme_penalty=0.02
```

It reports the useful share of the recorded selection and of the stage-1 top 10/30, lists labelled useful papers that were not selected with their stage-1 rank, and replays stage 1 from the stored similarities under `--set` overrides without the model or any API call. LLM judgements exist only for the recorded shortlist, so `top_k` and threshold changes still need labels on the papers involved.

For a controlled comparison with an earlier evaluation bundle, the reading-value replay requires an explicit mode and a new isolated output directory:

```bash
# Zero API calls: plan the expanded shortlist from the archived ranking.
uv run --frozen scripts/replay_reading_value.py verification/eval/RUN/evaluation.json \
  --plan-only --output verification/reading-value/RUN-plan

# Explicitly permit live abstract-screening requests; no SMTP or history writes.
# Requires OPENAI_API_KEY and OPENAI_API_BASE in the environment.
uv run --frozen scripts/replay_reading_value.py verification/eval/RUN/evaluation.json \
  --live --output verification/reading-value/RUN-live
```

The historical bundle is read unchanged, and an existing output path is refused. `--plan-only` produces a shortlist plan, not new recommendations. `--live` uses the current public screening configuration and saves its own isolated judgement cache and comparison artifacts; it does not retrieve body text or run the focus review/summary stage. Both modes label the output as a title/abstract screening preview. Old recommendations and archived scores support comparison, not new body-evidence claims. A completed abstract replay does not establish improved reading quality or a production-ready focus brief.

The `Preview reading-value selection from an archived week` workflow (`.github/workflows/replay.yml`) has no schedule and supports both manual dispatch and reuse. For a preview branch, the existing `Test` workflow provides a `replay_run_id` input that runs only this replay job and skips its ordinary delivery-verification job:

```bash
gh workflow run test.yml --ref BRANCH -f replay_run_id=ARCHIVED_WEEKLY_RUN_ID -f send_test=false
```

Once `replay.yml` is available for direct dispatch, `gh workflow run replay.yml --ref BRANCH -f run_id=ARCHIVED_WEEKLY_RUN_ID` invokes the same job. The referenced run must belong to this repository and still have the unexpired `weekly-brief-report` artifact containing `evaluation.json`. The workflow downloads it read-only, runs the replay with `--live` using the checked-out branch's profile and only the two LLM secrets, and uploads `reading-value-comparison` for 14 days. It does not send mail or write production delivery history, and it intentionally does not apply `CUSTOM_CONFIG` to this historical experiment. Dispatch through `test.yml` with `replay_run_id`, the skipped ordinary verify job, artifact download, real provider calls and result upload were verified in the two 2026-11-05 runs above; direct dispatch of the new `replay.yml` itself has not been tested.

Actions `CUSTOM_CONFIG` merges into the checked-out configuration, preserving new defaults only when the variable omits those keys. Explicit old `policy`, `top_k`, `profile`, focus/explore limits or `executor.max_paper_num` values still override the repository after deployment. Before enabling the new policy in production, back up the existing variable, compare its effective merge against the intended repository settings, and prepare a reviewed update that retains environment references and unrelated delivery/library settings. Do not blindly replace the variable or change it merely because the source branch changed. A repository-only configuration change does not prove which policy production runs. Credential values in the override must be environment references; literal keys/passwords are rejected without printing their values. Existing bare full-text confirmation instructions are normalized to numbered labels. Manual Test/preview dispatches use the selected branch, while scheduled runs use the default branch. Pull-request CI covers both `main` and `dev` targets.
