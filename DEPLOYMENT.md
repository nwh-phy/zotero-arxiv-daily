# Physics literature digest deployment

The fork runs on GitHub-hosted Ubuntu with Python 3.13 and CPU PyTorch. The weekly fork uses theme-balanced embedding ranking with explicit related Zotero references; the base configuration still offers the original legacy algorithm. Scheduled trigger: `15 0 * * 1` (08:15 Asia/Shanghai). GitHub may delay scheduled jobs; this is a trigger time, not a guaranteed mail arrival time.

## Repository settings

Actions Secrets: `ZOTERO_ID`, `ZOTERO_KEY`, `OPENAI_API_KEY`, `OPENAI_API_BASE`, `SENDER`, `RECEIVER`, `SENDER_PASSWORD`.
Actions Variables: `CUSTOM_CONFIG` (optional non-sensitive YAML merged over repository defaults), `SMTP_SERVER`, `SMTP_PORT` (465 default), `DELIVERY_ENABLED`.

`CUSTOM_CONFIG` must contain environment references for credentials, never credential values. The workflow does not print it. All credential values belong in Secrets.

The deployed language is Chinese. Abstract-confirmed facts and facts confirmed by the supplied full-text excerpt must be distinguished; the input is capped to 4,000 tokens and is not a complete-paper review. English titles, authors, arXiv publication date/journal metadata and original/PDF links are rendered separately. Summary length and required Chinese fields are validated; at most one repair request is made using the original evidence. Its feedback specifies the actual Chinese-character count, missing/duplicated fields and invalid evidence markers, including the exact permitted excerpt IDs. An empty initial response can use this same single repair; diagnostics never log model drafts. Failed, empty or still noncompliant summaries stop delivery; every named Chinese field must have a valid evidence label, an explicit speculation label or an unavailable-evidence statement. Full-text labels identify an existing supplied excerpt. These checks validate provenance and format rather than factual entailment; noncompliant summaries are never quietly replaced by English abstracts. Author affiliations are disabled to avoid a second LLM request per paper.

## Complete SMTP setup

Use the repository Settings / Secrets and variables / Actions pages, or `gh secret set NAME -R nwh-phy/zotero-arxiv-daily` with secure interactive input, for sender address, receiver address and SMTP app password. Set `SMTP_SERVER` and `SMTP_PORT` as variables. Never provide a mailbox login password or put credentials in YAML.

Run the `Test` workflow. Its native tests are offline; its live checks cover Zotero, CPU embedding, arXiv, ranking, LLM, Chinese summary, HTML rendering and SMTP authentication. Missing SMTP is explicitly BLOCKED. By default Test does not send email. The optional `send_test` input sends one explicitly labelled deployment test only after all requested checks and SMTP authentication pass; historical samples are labelled as such. SMTP acceptance does not prove inbox arrival. The optional `summary_only` dispatch input retests the summary stage after a summary-only fix; skipped stages must be assessed against the earlier full-run evidence. The full verification shares the 180-minute CPU budget used by weekly delivery; hundreds of abstracts can exceed 40 minutes on a GitHub runner. Verification artifacts are retained for 14 days. The abstract-only sample uses a real paper from the configured current arXiv window; a separate full-text sample checks section extraction and valid excerpt citations when available. Unavailable full text is explicitly SKIP; on empty RSS days, a separate arXiv API query supplies real historical records solely for verification. These are labelled as historical samples and never sent by the production workflow; an explicitly requested deployment test may send one labelled historical sample.

Only after SMTP authentication succeeds, set `DELIVERY_ENABLED=true` and manually run `Send weekly literature brief` to verify actual email delivery. If credentials are missing, preflight lists only their names. Until then, the weekly job is deliberately skipped.

## Operations and limits

Keep Alive commits a timestamp monthly to retain repository activity. Native CI tests exclude the model-download test; the Test workflow explicitly exercises the configured embedding model on Ubuntu. Both uv dependencies and Hugging Face downloads are cached. Jobs have bounded timeouts, and LLM retries are limited. Per-paper checkpoints are restored before processing and saved even after ordinary job failures; cache service errors do not block processing or successful-delivery markers.

No new candidates means no email. With delivery history enabled, an empty successful retrieval still advances its UTC coverage cursor. A China-date cache marker is saved after SMTP accepts the message, and delivery runs are serialized. This is best-effort duplicate suppression, not transactional exactly-once delivery: cache eviction, cache-save failure or interrupted SMTP acceptance can allow duplicates. Do not blindly rerun a delivery job when SMTP acceptance is uncertain. SMTP acceptance does not establish recipient inbox arrival.

Zotero access is read-only. Corpus filtering uses existing physics-oriented collection paths. No server, Docker or paid embedding resource is provisioned. The LLM reuses an existing OpenAI-compatible service; its availability and quota remain external dependencies.

Weekly delivery: Monday 08:15 Asia/Shanghai (UTC cron `15 0 * * 1`). The first production attempt retrieves all pages for new submissions in the preceding seven complete UTC days and records that attempted start before fetching. If this very first attempt fails, a later retry starts at that original boundary instead of forgetting the failed week. Attempted start and successfully completed coverage are separate; previews never create or advance either record. Later runs start at the last successfully completed coverage boundary minus a two-day overlap, including matching cross-listed categories. Failed weeks are backfilled rather than silently skipped; a gap over the configured 90-day limit stops explicitly until the limit is raised. Boundaries are UTC midnight (Beijing 08:00). Old-paper revisions are excluded. Abstracts are ranked with theme-balanced scoring and soft diversity penalties; full-text extraction is attempted only for the top ten. A delayed API index may omit papers; this does not guarantee exhaustive coverage. Timeout is 180 minutes for the larger weekly CPU workload.

Summary generation uses `kimi-k3-1` through the existing Responses service, with low reasoning effort and a 4096-token output budget. The summary itself remains 150–250 Chinese characters. The embedding model and seven-day retrieval window are unchanged; ranking uses the configurable theme-balanced policy described below.

The weekly brief now uses the China-edition Kimi K3 model `kimi-k3-1`. Its dedicated WorkBuddy key `zotero-weekly` is pinned to China edition and only allows that model. The key is stored solely in this fork's Actions OPENAI_API_KEY secret; the CC Switch provider remains unchanged.

## Recommendation, evidence and resume behavior

The fork enables `reranker.ranking.mode: theme_balanced`. Zotero paths are grouped at depth two (for example `20_主题/EELS` or `10_项目/博士衔接文章`). Each candidate is scored against up to three nearest references within each theme, weighted by actual elapsed days between Zotero additions with a 180-day half-life. Its highest theme score is the displayed relevance score. Multi-collection papers are counted once within each theme. Soft penalties reduce repeated winning themes and near-identical candidate abstracts; no theme receives a compulsory quota. The selected order can therefore differ from descending raw relevance. Emails identify the winning theme and related reference titles. These are embedding matches, not LLM-generated claims about relevance. The parameters are initial heuristics, not a measured improvement in personal recommendation quality; evaluate them against reading feedback. Set the mode to `legacy` to restore the original score/order.

Summary input remains capped at 4,000 tokens. TeX preambles/comments are removed, nested input/include files are resolved relative to the source bundle with cycle/depth/size bounds, and conclusion, results/discussion and methods sections are preferred over introductory text. Markdown headings and common plain-text headings are supported. When headings cannot be recognized, both ends of the body are sampled and labelled as unrecognized sections; this does not establish that a conclusion section was found. Bibliography and acknowledgements sections are excluded. The reader-facing email removes repeated abstract-confirmation tags, compacts full-text citations to `[E1]` and lists the cited excerpt IDs/section names in one source line per paper. Speculation and unavailable-evidence wording remain visible. The original summary and its complete labels are retained unchanged for validation and checkpoint reuse. Full-text claims must use an existing label such as `[全文片段确认:E1]`; unavailable IDs and bare full-text confirmation labels fail validation. Every field is checked independently for its label or explicit unavailability; these checks establish source availability and format, not semantic correctness of every claim.

`executor.progress_dir: .paper-progress` enables local checkpoints. Set it to `null` to disable. Checkpoints are partitioned by library ID and paper metadata/version, and store extracted body text, validated summaries and safe processing/error status. Credentials, resolved configuration and Zotero reference titles are not stored. Model/endpoint, prompt/quality rules, evidence-selection version or input changes invalidate summary reuse. Extractor changes require an `EXTRACTOR_VERSION` bump; changes to summary input or evidence selection require an `EVIDENCE_VERSION` bump. Repair-feedback changes that retain the same original input, policy and acceptance rules preserve already validated summaries; they do not require repeating successful work. A corrupt checkpoint is ignored. Files are written atomically; extraction can be reused when summary generation fails. Completed summaries are checked again before reuse and strict validation runs before delivery. Failed selected papers do not prevent the remaining selected papers from saving progress, but they prevent email delivery. Cache restoration never marks an email as delivered.

GitHub Actions restores `.paper-progress` from the most recent available repository cache and writes a new cache key per run/attempt, including failed runs. Cache eviction, cancellation or hard runner termination can lose progress; this is best-effort resumability. Locally, delete `.paper-progress` to start fresh. Overrides changing the progress directory must also update the workflow cache path. Coverage history and the SMTP date marker remain separate mechanisms; coverage/history correctness across hosted runners still depends on successful cache persistence/restoration.

## Coverage, duplicate suppression and SMTP uncertainty

The fork enables `executor.history_enabled: true` for weekly arXiv-only retrieval. History lives beside per-paper checkpoints, partitioned by library and receiver/subscription. After SMTP acceptance, all retrieved/evaluated paper IDs are remembered, including papers below the recommendation cutoff. This prevents the overlap window from recycling last week's unselected papers. Late-indexed records that have not been seen remain eligible. arXiv versions and HTTP/HTTPS URLs share an article identity. IDs are retained for 120 days; no overlap setting should exceed that retention window. A changed receiver/category/collection subscription starts an independent coverage history. Coverage only advances after successful delivery or a genuinely complete no-new-candidates run. Corrupt history fails closed, and a local POSIX lock prevents concurrent sends using the same history.

Before submitting a message, the intended batch is written to history with a deterministic Message-ID. A connection, TLS, authentication or explicit SMTP rejection clears that pending batch and allows a retry. A disconnect/timeout during submission leaves its outcome uncertain and prevents automatic resending. A failure during QUIT does not undo prior DATA acceptance. If SMTP accepted but history cannot be saved, the workflow date marker is still written when possible, and the pending batch must be reconciled. Neither a Message-ID nor a cache marker guarantees exactly-once SMTP delivery or recipient inbox arrival.

The `Reconcile uncertain literature delivery` workflow defaults to inspection and never sends mail. First inspect its pending batch ID, then check independent SMTP or recipient evidence. Only with that evidence, run it with the exact batch ID and `accepted` or `not-accepted`. A mismatch changes nothing. Locally, with the normal environment/configuration loaded, use:

```bash
uv run --frozen scripts/reconcile_delivery.py --outcome inspect
uv run --frozen scripts/reconcile_delivery.py --outcome accepted --batch-id EXACT_BATCH_ID
# Or --outcome not-accepted only after confirming rejection/non-acceptance.
```

Cache eviction, restoration failure, hard cancellation and the unavoidable SMTP/persistence gap can lose history. The protections are best effort on GitHub Actions, not a transactional delivery system. Keep independent evidence when investigating uncertain sends; do not clear history merely to make a rerun proceed.

## Preview and operational evidence

Run locally with `executor.dry_run=true`, or select `dry_run` when dispatching the weekly workflow, to render a preview without SMTP, delivery markers or coverage advancement. Required provider/library configuration still needs to be available. A preview may populate the reusable extraction/summary cache; it does not mark candidates as evaluated for delivery. A dry-run dispatch works while `DELIVERY_ENABLED=false` and ignores a prior successful same-day marker. Scheduled jobs continue to respect that gate. `executor.output_dir` defaults to `verification/brief`; `brief.html`, `brief.txt` and an aggregate `report.json` distinguish preview, no-candidate, failed, uncertain and SMTP-accepted outcomes. The weekly workflow retains report artifacts for 14 days and posts aggregate counts/duration to its job summary. HTML/plain-text artifacts contain recommendation/reference content and should be handled as personal literature data; resolved secrets/configuration are never included.

Actions `CUSTOM_CONFIG` now merges into the checked-out configuration, preserving newly added defaults when old variables omit them. Explicit settings such as `ranking.mode: legacy` or `history_enabled: false` still take precedence. Credential values in the override must be environment references; literal keys/passwords are rejected without printing the values. Existing bare full-text confirmation instructions are normalized to numbered labels. Manual Test/preview dispatches use the selected branch, while scheduled runs use the default branch. Pull-request CI covers both `main` and `dev` targets.
